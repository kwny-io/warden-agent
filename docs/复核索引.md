**这一轮学到的（可复用）**

- **「单跑绿、全量红」几乎总是作用域问题**，不是 flaky：两条用例读写同一批共享状态（这里是后端的`/approvals`），
  而断言的作用域是全页 → 别的用例留下的行会一起被命中。**先查定位器作用域，再怀疑并发时序**。
- **`toHaveCount(0)` 配「重试式断言」会掩盖竞态**：只要在某一帧恰好为 0 就算通过，
  于是"通过"取决于两个轮询的先后。要让断言**只有一种解释**（这里：待审批里没有、历史里有）。
- **`toBeInViewport()` 不能用来验「在滚动容器里可见」**：它比的是元素矩形与浏览器视口，
  被 `overflow` 容器滚出去的元素矩形可能仍在浏览器视口内 → 假绿。用容器与元素的**包含关系**判断。

## 2.8 第三十六批：多副本 e2e（真 PG + 6 个真后端进程 + 真浏览器）

> 起因：`README` 的「已知局限」写着「多副本仍未覆盖」，而它是唯一还没在**真环境**跑过的部署形态——
> 此前的信心来自「同一进程内两个 store 实例」的集成测试。这一批要求：两个**真进程** + 同一个真 PG +
> 真浏览器打开页面，三条证据链都真跑。

**新增 `web/e2e/multi-replica.spec.ts`（6 条）**：起 6 个真后端（共享档 2 / 对照档 2 / 限流档 2），
共用一个**每次运行新建的空 PG 库**：

| 用例 | 断言什么 | 为什么它能证伪 |
|---|---|---|
| 会话历史跨副本 | A 副本写消息 → B 副本的 `/messages` 与**从 B 打开的浏览器页面**都读得到 | 只在 A 的进程内存里就会红（“换副本还在不在”的真判据） |
| 事件跨副本 | A 上跑完一轮 → B 的 `/events/{run_id}` 续读到同一条 final | 等价于“浏览器在 A 上断了、重连被负载均衡分到 B” |
| 对照：关共享 | 关掉 `WARDEN_SHARED_STATE` 后 B **读不到** A 的事件 | 没这条，上一条可能是“事件本来就到处能读” |
| 幂等键跨副本 | 同 key 打到另一个副本 → 不执行第二遍、副作用只发生一次 | 幂等表在进程内存里就会重复执行 |
| 对照：关共享 | 关掉共享后同 key 打到另一个副本**会真的执行第二遍** | 证明上一条的差别**只**来自共享开关，不是幂等表坏了 |
| 限流计数跨副本 | 额度全局一份（3/60 下第 4 个请求被 429 拒，错误体 RFC7807 `RATE_LIMITED`） | 每副本各算一份时第 4 个仍会 200 |

**顺带补上第三十批「只修了一半」的竞态**（`src/warden_agent/store/pg_schema.py` 的 `serialized_schema_init`）：
第三十批把版本行写入改成 `ON CONFLICT DO NOTHING`，但 `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE`
序列在并发下仍会撞（后提交的事务在 `pg_type`/`pg_class` 上唯一键冲突）。现在是
`SELECT set_config('lock_timeout', %s, true)` + `SELECT pg_advisory_xact_lock(...)` 把整段迁移串行化
（事务级锁，随提交/回滚自动释放），版本行写入也改成幂等 upsert。回归：`tests/test_pg_concurrent_init.py`。

**教训（这一批真正的“可复用”部分）**：
- **两类 SSE 流的终态字段名不同**：`/chat/stream/{run_id}` 用 `type`、`/events/{run_id}` 用 `event`。
  只按 `event` 找终态 → chat/stream 上“永远读不到 final”，而且因为找不到终态，流会一直读到超时。
- **会话第一条消息永远是 `system`**：断言角色序列必须过掉它，否则 `rows[0]` 拿到的是系统提示词，
  看起来像“用户消息被写坏了”。
- **共享库会把无关用例串在一起**：限流计数按来源 IP 记在共享库里，而所有用例都从 127.0.0.1 发请求 →
  限流档必须用**自己那个空库**，“额度 3”这个前提才成立。
- **“说过修好了”要按“真场景”重测一遍**：版本行写入修了 ≠ 建表不撞；扩副本就是那个真场景。

**怎么亲手跑**（本机无 `psql` 时脚本自动走 `docker exec` 到 `warden-pg-test`）：
```bash

cd web && npx playwright test multi-replica      # 只跑多副本（34 秒）
```
⚠️ 多副本那 6 条**需要真 PG**：没有时 `test.skip` 跳过（不假装跑过）。

## 2.11 第四十二批：`mypy --strict` 这条 CI 门禁被上一批弄红了（10 个错同一行）

## 2.12 第四十三批：CI 三个红 job 的根因各不相同（假 High / 误判 / 时序坑）

## 2.13 第四十四批：三个红 job 的**下一步**根因（三次「碰巧成立」的前提）

**先说清与 §2.12 的关系（别把两份诊断看成矛盾）**：CI 一个 job 是**线性步骤表**，
第 43 批修的是各自**第一个**失败步骤（bandit 假 High / 启动被守卫拦住 / 钉底时序），
本批修的是重新跑之后暴露的**下一步**。证据：第 43 批那三处修法已在代码里且本地验过
（bandit 退出码 0、冒烟能启动、`ChatView.scroll.test.tsx` 4 条 + e2e 绿），但它们不足以让 job 变绿。

### 1. security：密钥扫描器被**靜默关着**（本批最严重的一条）

- `.gitleaks.toml` 用的是新版写法 `[[allowlists]]`（复数），而 CI 钉的 v8.21.2 **靜默忽略**它。
- 实测（本地同版本镜像，扫全历史）：不传 `--config` 时 7 处命中照报——因为 gitleaks 只在**进程 cwd**
  找 `.gitleaks.toml`，**不会**去 `--source` 指向的目录找；传了配置但用复数写法时，
  连 `regexes=[".*"]` 这种 catch-all 都清不掉一条命中 → **配置一直没生效**。
- 改法：单数 `[allowlist]`；CI 显式 `--config /repo/.gitleaks.toml`；只按**值**放宽
  （`paths` 与 `regexes` 是 **OR**，写上 `paths` 会让 `tests/test_approval_separation.py` 与
  `tests/test_redaction.py` 变成**永久盲区**）；保留 `[extend] useDefault`（自定义配置会替换默认规则集）。
- **反向对照**（新增步骤）：往临时目录丢一个**未被放宽**的高熵假密钥，必须仍被报出，否则该步骤失败。
  → 从此「扫描器被关掉」会以**红灯**现形，而不是静默通过。

### 2. quality：两条用例拿**宿主环境**当契约

- `tests/test_ci_pg_guard.py`：验「非 CI 分支」的用例直接读宿主 env，而 runner 上 `CI=true` 是环境默认值 → 走错分支。
  改成用例自管环境（`monkeypatch.delenv("CI")`）。
- `tests/test_release_scripts.py`：用 `path="/usr/bin:/bin"` 表达「这台机器没装 docker/kubectl」
  ——在 Windows 开发机上碰巧成立（那两个路径压根不存在），在 runner 上不成立。
  改成 PATH 指向**空目录**并**当场自检** `shutil.which(tool, path=path) is None`；
  脚本要的外部命令用 bash 函数顶替；`exec bash` 改绝对路径。
- 反向用例：CI 环境下**没有** junit 报告必须红 ✓。

### 3. container：冒烟验的不是**部署形状**

- 冒烟用**单 key** 起容器（主体名默认 `demo-user`），却去读 **admin-only** 的 `/metrics` → 必然 403。
  **产品没错**，是**脚本的配置不是部署的配置**。
- 改法：按真实部署配两个身份（`WARDEN_API_KEYS="smoke-admin:…,smoke-viewer:…"` +
  `WARDEN_ADMIN_PRINCIPALS=smoke-admin`），并补断言「**非管理员读 `/metrics` → 403**」。**不放宽断言**。
- 这条断言补上了一个此前的**覆盖空白**：`/metrics` 的 admin-only 策略**此前没有任何用例**
  ——而它正是那个 403 被发现的原因。

### 4. 补记：那条反向对照**本身是坏的（永真）**——本批唯一“写错了却被当场抓住”的地方

- 判据写成 `grep -q "leaks found"`，而“无命中”时 gitleaks 输出的是 `no leaks found`——**也含**该子串，
  实测两种情形都匹配 → 这条对照**从出生起就在通过**，什么都没验（假绿）。
- 另一层：第一版对照值 `sk-live-<32 hex>` **连默认规则集都不命中**（exit=0），前提也不成立。
- 现在：`scripts/gitleaks_reverse_control.sh` ① 用**退出码**判（1=有命中），
  对照值改成与被放宽夹具**同形状、不同值**；② 自带**负面对照自检**（catch-all allowlist 下对照必须消失）。
  ② 已当场抓到第二个问题：容器内 `/cfg.toml` 被 MSYS 转成 `C:/Program Files/Git/cfg.toml`（配置没加载）。
- 教训：**守卫自身也要能被证伪**；永远通过的守卫比没有守卫更糟（它把“没人守着”伪装成“守住了”）。

## 9. 「假绿」审计：静默跳过 / 空断言（2026-09-29）

问题：**测试套件里有多少绿色是假的？** 两条最常见的假绿来源是"静默跳过"和"没有断言的用例"。

### 怎么查的（可复现）

用 AST 遍历 `tests/**/*.py` 里所有 `test_*` 函数，判定"这个函数里有没有任何断言"——
命中任一即算有断言：`assert` 语句、`pytest.raises(...)`、`*.fail(...)`、`assert*` 开头的辅助调用；
同时记录函数体内的 `pytest.skip` / `pytest.xfail`。

### 结论

| 维度 | 结果 |
|---|---|
| `test_*` 函数（静态计数） | **1278 个**（pytest 实际收集 1475 条，差值是参数化展开） |
| **真·无断言用例** | **0 个** |
| 静态扫描的误报 | **1 个**：`tests/test_store_interface.py:54` 的 `test_postgres_存储全量协议`——断言全在 helper `_postgres_full_flow()` 里；该用例 docstring 自己就写明"会被无断言的静态扫描命中，这是已知误报" |

### 补充：「假绿」的第三种来源——**结论取决于你从哪个 shell 启动**（第四十七批，2026-10-03）

本节上面两条防线问的是"用例里有没有断言""断言够不够严"。第四十七批撞上了**第三种**假绿/假红，
两条防线都问不到：**同一个提交、同一台机器、同一个命令，换一个启动环境结论就翻转。**

| 触发条件 | 现象 | 根因 |
|---|---|---|
| 从 cmd.exe / PowerShell 启动 pytest | `tests/test_release_scripts.py` 的 18 个用例全红：`execvpe(/bin/bash) failed: No such file or directory`（子进程 args[0] = `C:\Windows\System32\bash.EXE`） | `shutil.which("bash")` 只回答"PATH 里有这个名字"，不回答"它跑不跑得起来"；那个 `.EXE` 是 WSL 转发器，没有发行版时**能启动但立刻失败** |
| PATH 收窄成 `System32;Windows`（模拟没装 Git 的机器） | 换掉假 bash 后仍 12 failed：`assert 127 == 0` | 测辅助的 `_run()` 用 `env = dict(os.environ)` 把宿主 PATH 原样交给子 bash；`sed`/`dirname` 在 `Git\usr\bin`，不在 PATH 里 |

**为什么它比普通红更糟**：这 18 个用例测的是 `scripts/pin_image_digests.sh` 与 `scripts/rollback.sh`
——只在发布/回滚真出事时才运行的脚本。假红灯会让人养成"这个文件本来就红"的习惯；
假绿更糟。**结论取决于"你从哪个 shell 启动"的测试，等于没测。**

**怎么修**（`tests/test_release_scripts.py`）：探测改成**真跑一次**（`bash -c "exit 0"` 返回 0 才算有 bash）→
按 `which` → `Git\usr\bin` → `Git\bin` 取第一个**能跑**的 → **查文件**确认 `sed` 在哪（不猜路径）→
把 coreutils 目录**显式**塞进子进程 PATH（不再继承宿主环境）。外加一条元测试
`test_wsl转发器不会被当成可用bash`：它**故意不依赖探测结果**，所以在"探测本身写错"的机器上照样执行并变红
——否则它只是又一个会被同一个 bug 一起 skip 掉的摆设。

**亲手证伪（本机可复现，下面每条都实跑过）**：

- 正常环境（Git Bash）：`uv run --frozen pytest tests/test_release_scripts.py -q` → **19 passed**。
- 模拟"PATH 里没有 `sed`"的机器（同时让 `System32\bash.EXE` 是 WSL 转发器，两个陷阱都在场）：

  ```bash
  PATH='/c/Users/g1534/.local/bin:/c/Windows/System32:/c/Windows' uv run --frozen pytest tests/test_release_scripts.py -q
  ```

  → **19 passed**（改动前同一环境：**12 failed**，`assert 127 == 0`）。
  注意 PATH 必须写成 MSYS 风格（`/c/...`）：写成 `C:\...` 的话 bash **连 `uv` 都找不到**（`command not found`，退出码 127）——
  一条跑不起来的"可复现命令"比没有命令更坏。
- 从 cmd.exe / PowerShell 启动（真实触发环境，`shutil.which("bash")` → `System32\bash.EXE`）：**改动前 18 failed**。

**本机实跑（第四十七批：win32、本机没起 PostgreSQL）**：`1615 项收集 / 1571 passed / 44 skipped / 561.8 秒`，
覆盖率 **86.93%**（门槛 86.0%，`Required test coverage of 86.0% reached`）。
那 44 条跳过来自 **40 个条件跳过点**，原因只有三类：需要真 PostgreSQL（绝大多数）、
win32 不支持创建符号链接、PATH 里没 `pg_dump`/`pg_restore`。
**所以"跳过数"是环境的函数**，别跨机器/跨批次直接比 —— 上表那行 `4 skipped` 与这里的 `44 skipped`
不是矛盾，是两台机器的 PG 起没起。CI 侧由 `scripts/check_pg_tests_ran.py --junitxml` 保证
PG 用例在 CI 里**真的跑了**（否则"全绿但一条 PG 用例没跑"就是最大的那种假绿）。

**本批的 19 条发布/回滚用例在 cmd.exe 环境实测 `19 passed`**（junit 里 `tests.test_release_scripts` 全 PASS），
即改动前那个红环境已被真实验证过一遍 —— 不是"换了台机器就没红"。

**顺带发现（属于本节主题）**：`pyproject.toml` 的 `addopts` 已经自带 `-q`，命令行**再**传一个 `-q`

所以本轮有几条命令跑完只剩退出码、拿不到计数——**只有退出码在所有模式下都可信**。
要计数就用 CI 的那条命令（`--tb=short -rs -p no:cacheprovider --cov=... --junitxml=...`，不要加 `-q`）。

### 第六种来源：**接线处没有守卫**——「文件都在」制造的安全感（第五十二批，2026-10-03）

|---|---|---|

- **保留期校验写死在断言里**（`30d` 字面量 + 只查 compose）⇒ 规则里的真实窗口改了，守卫不知道。

**一句话**：守卫绿不代表守住了；**守卫要被变异验过一遍，才算存在**。

### 第七种来源：**占位符是「配置没填」的一个合法取值**——「没填」和「填了但没生效」在代码里长得一样（第五十三批，2026-10-03）

| 现象 | 机制（两段合起来才完整） | 于是表现成 |
|---|---|---|

|---|---|---|
| 文档（CHANGELOG + `docs/operations.md`）写了 `--limit N` / `--limit 0`，而 `cli.py` 的 `stuck` 子命令**从来没有这个参数**（只有 `--all`） | 这批的四条新守卫钉在三件事上：默认口径**有上界**、`--all` 能给全量、`--json` 少给说了话（走 stderr）。**没有一条问过「文档承诺的那个参数真的存在吗」** | 本批的主题是“少给了要能看出来”，而**“要全量”的逃逸口自己就是句空话**：值班的人拿不到完整清单，只能看到“另有 4980 个未列出”，而命令直接以退出码 2 失败（“失败”和“参数写错”在 cron 里长得一样） |

**判据**：改副本的副本也会漏——**逃逸口本身也得有守卫，而且要钉在 argparse 的表面上**
（`option_strings`），不能钉在自己写的文档上；钉在文档上等于把文档当实现。
修法：`cli.py` 加 `--limit N`（`0` = 不设上限，与 `--all` 同义），
把“限几条”的计算收到 `_stuck_limit()` 一处（三处消费路径不再各自解释“0 是什么意思”）。

**本批的守卫**：`tests/test_cli_stuck_notify.py` 本就 4 条行为守卫，另加
`test_文档里写的_stuck_参数必须真的存在`——从 `docs/operations.md` 里抓与 `stuck` 同行的每个 `--flag`，
逐个要求在 `stuck` 子命令的 `option_strings` 里存在；再加 `--limit 3` / `--limit 0` /
`--json --limit 3` 三条行为断言。变异 E（去掉 `--limit`）→ `unrecognized arguments`（退出码 2）；
F（`--limit 0` 不再当作“不设上限”）→ 断言 `101 == 1`。

**证据等级**：真 `cli.main()` + 真 sqlite 存档库（5000 个 Run）+ 真 stdout/stderr/退出码；
真投递另用回环上的真 `http.server` 接收端验出网 body（6 511 字节，修复前是整份 JSON ≈1.29MB）。

#### 第十一种来源：**安全约定只写在文档里**——代码里没有一行保证它（第六十批，2026-10-04）

第五十八批建 `scripts/k8s_rollback_drill.sh` 时，我在 `deploy/k8s/README.md` 与脚本文档区写了
「本演练不会碰 `warden`」。第六十批自查把假 docker 放进 PATH（记录 argv）去跑**真脚本**，看到的是：

| 传参 | 脚本实际会干什么 | 文档怎么说的 |
| --- | --- | --- |
| `DRILL_NS=warden`（= 清单声明的那个） | 在**生产**命名空间 `set env deploy/warden-agent WARDEN_DRILL_MARK=1`（改生产负载模板），结束时 `kubectl delete ns warden --wait=false` | 「本演练不会碰 `warden`」 |

**判据**：一句话要成为契约，必须有一行**代码**能让它失败（守卫 / 断言 / 拒绝执行），
否则它只是注释；而「名字里带 `drill`」这种**人写的约定**，机器不会检查——
把它写成 `case` 语句，约定才存在。同族的两个变形：

- **入口也要把「我为什么可以这么做」写清**：`kind_api_forward.py` 把「端口被占」与
  「容器创建失败」这两种事实合成同一个 `except`，于是**成功**（上一次的转发还活着）
  被报成**失败**。
- **守卫自己会撒谎比没有守卫更危险**：正则里的「宽」不等于「对」——`["']?` 让
  `test_脚本里不许用反引号` 对无引号 heredoc 变聋，而它平时是绿的，给人一种
  「已经被看着」的错觉。它放过那 3 处合法反引号是误打误撞，不是看懂了 heredoc。

**本批的守卫**：`tests/test_release_scripts.py` 新增 5 条——4 条用**假 docker 驱动真脚本**
（拒绝在清单声明的命名空间上跑 / 名字必须自己说清它是演练 / 不删不是自己创建的命名空间 /
自己创建的必须带标记）+ 1 条**反自我**用例 `test_反引号守卫自己不许聋`；
真集群实测 6/6（含新增的「生产命名空间一个字节都没变」）。

**变异 D 的对象是一行可能没有常驻守卫的逻辑**：「清理失败翻转结论」——它的触发条件是
「6 个用例全过 **且** `delete ns` 失败」，而 4 条假-docker 用例里桩什么都不答、用例必然红。
结果（是否真的无守卫、以及用真集群怎么补的）写在 CHANGELOG 第六十批的变异段里，不在本文档里猜。

#### 第十二种来源：**判据的精度与范围，就是它实际能守住的东西**（第六十一批，2026-10-04）

同一个词「校验」，在三处地方含义完全不同，而三处的"绿"都是真的——只是**绿的边界**比人以为的小。

| 门禁 | 它挂/比到什么精度 | 结果 |
| --- | --- | --- |
| CI 的 `kubeconform -strict` | **只挂 `deploy/k8s` 一个目录** | `deploy/observability` 的两个 CR 不在职责内；`matchNames` 写成 `matchName`（少一个 `s`）→ 读 `deploy/` 的 72 个用例全绿 |
| `deploy/` 的那 72 个用例 | 查的是「我们的要求」：标签、Secret 键、规则正文与 `alerts/*.yml` 逐条一致、promtool 真求值 | **不查字段合法性**——而 CRD 是结构化 schema，未知字段被**静默剪掉** ⇒ apply 成功、字段没了、行为退回默认值 |
| `tests/test_mutation_shards.py` 的"逐字节还原" | 实际比的是 **`read_text()` 归一化后的文本** | 工作区副本已被写成 **CRLF** 而它看不见（`git diff` 也会替我们归一化）；声称的"逐字节"是**文本**级 |

**判据**：问一条门禁「挂了什么、比到什么精度」——挂某个目录就只守那个目录；比字符串就只守字符串；比文本就看不见换行符。
反过来说，**「没人写校验」与「校验的范围和意图不同源」会给出一模一样的绿灯**，而后者更难发现（因为确实有东西在跑）。

**本批的三个对应动作**：① 判据直接钉在 CRD 的 schema 上（且 schema 的**字节**被 sha256 钉住）；
② 加一条**范围的守卫**——盘上任何 `monitoring.coreos.com` 的 CR 清单没进校验名单就红（防"新加的文件没人管"重演；实测新增第三个 CR 时，逐个文件校验仍绿，只有它红）；
③ 把声称的"逐字节"做成真的逐字节（并断言不引入 CRLF）。**职责范围要写进文档**：
`deploy/observability/README.md` 与 README 的 CI 一节都写清了 CI 那条 kubeconform **只挂 `deploy/k8s`**，
以及为什么**不**给 CI 加一条"运行时去网上取最新 schema"的校验（第二个不确定的判据会在与改动无关的提交上变红，假警报会让人开始忽略门禁）。

#### 第十三种来源：**「选不中」是一个合法的空集，不是错误**（第六十二批，2026-10-04）

K8s 的选择器是**集合运算**，不是外键：它不要求"被选中的对象存在"，因为"先建策略、后建负载"
本来就是合法的部署顺序。于是"指向谁"这件事**没有一处会报错**——错的是字符串，空的是集合，
而**空集合完全合法**。

| 对象 | 选不中时的现场表现 | 人第一反应 |
| --- | --- | --- |
| `PDB.spec.selector` | `kubectl get pdb -o wide` 只显示 `ALLOWED DISRUPTIONS 0`（真选得中的是 1），而**健康**的集群在滚动更新期间同样是 0；`kubectl drain` 照删 | 「drain 怎么这么顺」——看不出"保护没生效" |
| `NetworkPolicy.spec.podSelector` | 管的是一个空集合：你以为"默认全拒 + 白名单"在生效，实际**没有任何约束** | 「策略我都写了」——比没有策略更危险 |
| `ServiceMonitor.spec.selector` | `up{job=...} == 0` | 「服务挂了？」——真实告警被淹没 |
| `Service.spec.selector` | EndpointSlice 里没有一个就绪地址，而 Pod 全绿 | 「Pod 都好着呢」 |
| `Ingress` 的 backend 端口名 | 503 | 「后端挂了？」 |

**判据**：凡是"A 指向 B"的字符串，都要问一句「**指向不存在的东西时，谁会报错？**」
——如果答案是"没有人"，那这条指向就必须有一条断言，而且断言要**从事实源推出来**（不抄第二遍）。
同族还有一类**语义**错（字符串没错、值错）：`PDB.minAvailable ≥ replicas` 时任何自愿驱逐都会被拒，
`kubectl drain` 永远卡住，现场表现是"节点维护做不下去"，不是"PDB 配错了"。

**连带发现（同一种「没人报错」）**：清单**文件本身被删掉**时，谁会红？我当时的推理是
「两个守卫都用 `glob("*.yaml")` 遍历盘上存在的文件 ⇒ 删了没人管」——**推理错了**。
真跑一遍（13 个文件逐个拿掉 + 跑守卫）：**13/13 全红**（10 条断言红 + 3 条收集期红）。
教训不是那个结论，而是：**推理出来的盲点，也要跑一遍再写进文档**。

#### 第十四种来源：**判定用的那把尺子自己是谁，从来没人问过**（第六十三批，2026-10-04）

“门禁挂了”和“门禁绿了”这两句话里，都隐含一个前提：**那句话是某个确定的程序说的**。
而容器引用是「字符串 + tag」，tag 是**可变引用**——上游重推同名 tag，
**不会改变本仓任何一个字节**，任何 diff、任何审查、任何守卫都看不见。

| 被执行的程序 | 引用形式（改动前） | 浮动 tag 的现场表现 | 人第一反应 |
| --- | --- | --- | --- |
| kubeconform / gitleaks / trivy / promtool | `docker run ghcr.io/…:vX.Y.Z` | 今天绿 = **某个版本**绿；上游重推同名 tag 就换了程序，CI 输出里看不出来 | 「门禁绿了」——但不知道是哪个程序绿的 |
| CI 的 `services: postgres` | `image: postgres:16-alpine` | 集成测试连的是另一个小版本 | 「PG 口径过了」 |
| `scripts/gitleaks_reverse_control.sh` | 与门禁**各写一份 tag** | 两份迟早会对不上，而两边**谁都不会报错**⇒ **反向对照变成空证** | 「反向对照也绿了」 |
| `scripts/mutation.sh` 的变异容器 | `python:3.12-slim` | 变异评测跑的是另一个解释器 | 「变异分片上去了」 |

**判据**：凡是“门禁执行一个外部程序”，都要问一句「**这个程序的身份（digest）写在哪？**」
——如果答案是“只写了 tag”，那这个判定**不可复现**，而且**不会有人报错**。
同一条判据要分两面看：**执行面**（真跑的）必须钉 digest；**文档面**（给人复制的手工命令）
只要求 tag 不漂移（改历史记录会把记录改假）。

**连带发现**：① 反向对照与它要证明的那件事**必须是同一个 digest**（否则证明不了任何事）；
② 镜像站的 digest **不能**当权威——实测同一个 `postgres:16` 在上游名下是 `f1c337…`、
在 `docker.m.daocloud.io` 名下是 `a3b7f4…`，镜像站自己重签名了 manifest；
③ 交付面（Dockerfile/清单）与门禁面是**两条轴**：交付面早就有 `scripts/pin_image_digests.sh`
的纪律与守卫，而门禁面一点也没有——**同一个仓库里两条轴的政策不一致，而没人发现**。

**教训**：这批我自己的四次错都是同一个形状——**把一次窄查询、或一次没跑的推理当成事实**，
其中最贵的一次是：调试脚本自己写错了（循环里提前 `break`），打出“扫到 0 条”，
把我往错方向送了一轮。**仪器坏了，要先验仪器**。

#### 第十五种来源：**「等等再钉」可以永远不钉**（第六十四批，2026-10-05）

上一批把**门禁面**的镜像钉住了，同时顺手发现交付面有同形状的半个空洞，写进了「已知限制」。
这批把它封掉——因为「已知限制」这四个字本身就是一个**没人守的口子**。

现场：`deploy/**` 与仓库根 compose 里 **7 处**外部镜像引用，钉住的 **0 处**。而
`scripts/pin_image_digests.sh` **自动**钉的只有 Dockerfile 的 `FROM`；`deploy/**` 的 `image:`
要有人在命令行**显式**传 `--also <ref>` / `--app-image <ref>` 才会被钉。
也就是说：**流程是有的，但它依赖人记得传参数，而没有任何东西守着这件事**。

| 谁 | 引用形式（改动前） | 现场表现 | 人第一反应 |
| --- | --- | --- | --- |
| `deploy/k8s/backup-cronjob.yaml` 的 postgres | `postgres:16-alpine` | CI 集成测试跑的是 `…@sha256:cf78e766…`，备份 Job 跑的是浮动 tag ⇒ **「CI 验过的那个」与「备份时真跑的那个」是两回事** | 「备份配好了」 |
| `deploy/observability/docker-compose.yml` 4 处 | `prom/prometheus:v2.55.0` 等 | 演练栈今天拉起的是 A、明天是 B，而演练记录上写的是「同一个环境」 | 「演练复现过了」 |
| `deploy/k8s/*.yaml` 的 2 处 | `REPLACE_ME/…` | 发布时由 `--app-image` 回写，**这个必须留着**（写假 digest 反而更坏） | — |

**判据**：凡是「发布 / 演练 / 巡检」清单里出现的**外部**镜像引用，都要问一句
「**谁保证它和昨天是同一个东西？**」——如果答案是「发布流程会处理」，
那要接着问「**那份要处理的清单写在哪里？谁在守它？**」。两问都答不出来，就是这条轴上的洞。

**改法**（不靠文档、靠静态守卫）：`scripts/check_pinned_images.py` —— 每个外部 `image:` 要么
`<ref>@sha256:<64位>`，要么进 `deploy/IMAGE_LEDGER.yaml` 台账（`image`/`added`/`reason`/`review_by`
齐全、未过期、不重复、不是孤儿）。CI 里是一条独立步骤，**不需要网络也不需要 docker**，
本地跑同一条命令就能复现 CI 的判定。

**连带发现**：① 我自己写的守卫**有三处会撒谎**——全同字符的占位 digest（`sha256:000…0`）会
被判成「钉住了」，而拉取时是 `manifest unknown`（Pod 从未起来过）；`image: ${REGISTRY}/app:1.0`
这类变量插值守卫**看不见**，永远绿；台账条目变成孤儿时不报，于是台账会腐化到没人看得懂。
② **允许「推日期」，但必须给得出理由**：推日期等于承认这次复核没做，所以过期报错里
直接给出两条出路（钉住 / 重新评估并改日期）。
③ 我的测试夹具写了 `sha256:` + `"1" * 64` 而被判红：**守卫对了、用例错了**——
这类「守卫比用例对」的时刻必须当场分辨清楚，否则很容易为了让它变绿去放松守卫。
④ **我新写的 docstring 把 tag 写飘了，被上一批的守卫抓住**：第一次全量 `1 failed` ——
`tests/test_ci_tool_pinning.py::test_文档里引用的版本不漂移` 报 `scripts/check_pinned_images.py:17`
（台账 `16-alpine` vs 实际 `16`）。修法**不是**把文档对齐台账（那会把没测过的 tag 说成测过的），
而是**把 tag 从这句里去掉**：机制（镜像站会重签名 manifest）不依赖具体 tag。
这也暴露了那条守卫的边界：`_SCAN_DIRS = (".github", "scripts", "tests")` 且 `_FILE_SUFFIXES` 不含 `.md`
⇒ `README.md` / `CHANGELOG.md` / `docs/**` / `deploy/**` 里的 tag 漂移**目前无人守**
（本批 `IMAGE_LEDGER.yaml` 注释那句就落在范围外，是我按同源原则手改的）。留给下一批的判据：
把扫描范围扩到 `.md` 与 `deploy/`，并先清掉它翻出来的历史写法。
⑤ **差点在后台全量跑着的时候改文件**：要改的 `check_pinned_images.py` 正是那批用例
**以子进程方式执行**的文件，边改边跑会让结论不可信。已 kill、确认进程死了再重跑。
教训：**要改的文件，先改完再跑全量**（文档同理：`test_config_surface.py` / `test_changelog_structure.py` 会读 README 与 CHANGELOG）。

**验证**（两口径全量，与 CI 同款命令；本批改了**零行 `src/`**）：真 PG **1739 passed / 4 skipped / 0 failed**
（614.96s，覆盖 **90.31%**）、无 PG **1699 passed / 44 skipped / 0 failed**（573.70s，覆盖 **87.08%**，门槛 86%）；
两口径收集数都是 **1743**（上一批 1728 ⇒ **+15**，全部来自本批新增用例）。

**已知限制**：台账里那 4 个演练栈镜像**仍然是浮动 tag**（本机到 `registry-1.docker.io` 直连不通
`net/http: TLS handshake timeout`）——本批保证「不再无声地漂」，不是「已经钉死」；
`review_by: 2027-01-03` 过了守卫就红。另：镜像站的 digest **不能**当权威
（本批实测同一个镜像在镜像站名下与上游不是同一个 digest）。

**教训**：一条纪律如果**只写在文档里、只在有人记得时执行**，它就不是纪律，是愿望。
「已知限制」这个词也一样：写下来不等于有人会回来处理它——
**要么变成断言，要么变成台账（带期限）。**

#### 第十六种来源：**「跳过」在报告里长得像「成功」**（第六十五批，2026-10-06）

「门禁是绿的」这句话里藏着两类完全不同的东西：**验过了**，和**根本没跑**。这两者在退出码上
是同一个值、在 CI 的总结行里也是同一行 `... passed, N skipped`。区别只在有没有人真去数那个 `N`。

现场（三个形状，同一个仓库）：

1. `tests/test_alert_rules_evaluated.py:193` 的 `test_promtool真值求值通过` 是唯一能把
   `*.rules.test.yml` 交给 promtool **真求值**的地方；它的门控 `_promtool_available()`（:180）
   跑 `docker images -q prom/prometheus:v2.55.0`，拿不到就 `pytest.skip()`（**测试故意不联网**）。
   而 `.github/workflows/ci.yml` 的 `quality` job 里**一条 `docker pull` 都没有**
   （promtool 那一步在另一个 job `container`）⇒ **这条用例在 CI 里每天跳过、CI 每天绿**。
   最坏的一点：跳过的那条，正是唯一能证「表达式语义对」的那条（第五十九批
   `WardenHighLatencyP95` 阈值 2s 高于最高有限桶 1.0 ⇒ 永远不响，就是这么活下来的）。
2. 仓库已经为「PG」这一条轴造了防静默跳过的守卫（`scripts/check_pg_tests_ran.py`），
   但**只有这一条轴**——同形状的洞在别的轴上一个守卫都没有。
3. `tests/test_store_interface.py` 自己拼 PG 连接（`host="localhost", password=""`），
   不走 `tests/test_postgres_integration.py::_pg_params()`：切「无 PG 口径」时它还在连真库，
   而 PG 换端口时它连不上 ⇒ **静默跳过**（第五十二批修过的形状，漏了这个文件）。

判据（两问）：

> 凡是门禁里**可能 skip** 的地方，都要问：**「它在 CI 里到底跑了没有？谁保证？」**
> 如果答案是「本机跑过」，接着问 **「那台机器上跑的是 CI 还是我？」**；
> 如果答案是「CI 里这个场景不成立」，接着问 **「这个『不成立』有期限吗？谁在到期时红？」**

机制（两问都答不出时的做法）：

- **跳过必须有签字**：`scripts/check_skipped_tests.py` 读主 pytest 产出的 junit，
  要求每一条 `<skipped>` 都在 `tests/SKIP_LEDGER.yaml` 里有条目。**不是手写文件清单**——
  谁新增一条「本机有才跑」的用例，它就自动出现在 junit 里 ⇒ 守卫自动红。
- **签字是一条承诺，而且分方向**：`allowed_in: [local]` = 本地可以跳、**CI 里必须真跑**；
  `allowed_in: [ci]` = CI 里场景不成立、那**本地**必须真跑；允许在门禁里留空洞的条目
  必须带 `review_by`——**空洞必须有期限**。
- **位置也是机制**：「预热镜像」必须排在产出 junit 的 Pytest **之前**、签字守卫排在其后。
  这条顺序由用例钉住（`tests/test_skipped_tests.py::test_预热镜像那一步必须留在Pytest之前`）：
  删掉预热，求值用例又会静默跳过。
- **账本要能被自己验**：拿真 junit 在两个方向上都验过——本地口径 `rc=0`（跳过全有签字），
  同一份 junit 换 `CI=true` ⇒ `rc=1` 并逐条点名「只允许本地跳却在 CI 里跳了」的用例。
  这批之前，**没有任何程序会红**。

**口径的元教训（本批现场撞到的）**：`_promtool_available()` 用 `docker images -q`，它需要
**docker 守护进程在跑**，不只要求镜像在本地。于是同一份命令、同一台机器，跳过数可以是
**44 或 46**——差别只在引擎状态。所以「无 PG 口径」的定义必须写成
**「docker 引擎在跑、只把 PG 容器 `docker stop` 掉」**；否则「跳过数」这个判据本身就不稳定
（第五十二批那句「判口径永远看 `skipped` 是 4 还是 44」也需要这条前提）。
