# API 版本与弃用策略

> 这份文档回答两个问题：**版本号怎么变**、**旧版本还能用多久、怎么通知**。
> 没有这份政策时，客户端只能靠"猜"——而"猜错"的代价是拿着旧假设去读语义已经变了的响应。

## 一、版本形态

响应头 `X-Warden-Api-Version`（当前 **1.0**）标出服务端实际提供契约的版本；所有响应都带它。

客户端可以在请求里带 **`X-Warden-Api-Version`** 声明自己按哪个版本写的：

| 客户端声明的版本 | 服务端行为 |
|---|---|
| 不带该头 | 按**当前**版本处理（等于声明的就是当前版本） |
| `1.0`、`1.7`（主版本受支持） | 正常处理；响应头回服务端实际版本 |
| `2.0`、`v1`、`abc`（主版本不支持 / 形态不对） | **400 `UNSUPPORTED_API_VERSION`** |

**为什么主版本不支持时直接报 400，而不是"尽力处理"**：
版本号是客户端在声明"我按这套语义写的"。服务端若装作没事继续处理，
调用方会拿着过时的假设去解释一个语义已经变了的响应——**静默错读比明确报错危险得多**。
（同一条取向见鉴权的 fail-closed：宁可拒绝启动，也不要有默认弱密钥悄悄上线。）

## 二、什么算破坏性变更（→ 主版本 +1）

- 删除或重命名端点 / 字段；
- 改变字段的**语义**（含义变了但名字没变——最容易被忽略、也最容易坑人）；
- 收紧取值范围（原本接受的输入开始被拒）；
- 改变默认行为（例如默认模型、默认限流口径）；
- 改变错误码 / 状态码的含义。

**不算破坏性**（→ 次版本 +1，主版本不动）：

- 新增端点、新增可选字段、新增错误码；
- 放宽取值范围；
- 新增能力开关（默认关）。

## 三、弃用流程（旧版本还能用多久）

1. **宣布**：在 `CHANGELOG.md` 里写清"哪个版本弃用、替代是什么、何时移除"。
2. **过渡期**：被弃用的主版本**至少保留一个次版本周期**，且期间行为不变。
3. **通知**：调用方若声明了被弃用的版本，响应里会带
   `Deprecation: true`（RFC 9745 允许在具体日期未定时用 `true`）。
4. **移除**：移除时主版本 +1，旧主版本开始返回 400 `UNSUPPORTED_API_VERSION`。

> ⚠️ **当前状态（如实说）**：过渡期通知头（`Deprecation`）与"被弃用版本清单"**还没实现**——
> 现在只有"主版本支持与否"的判定。项目至今只有 1.0 一个版本，尚未发生弃用；
> 真要做第一次弃用时再补第 3 步（连同自动通知一起加）。

## 四、兼容性怎么被守住

- `tests/test_web_contract.py`：所有响应都带版本头；幂等 / 错误码契约。
- `tests/test_api_versioning.py`：主版本判定、形态不对的版本号、不带头的默认行为。
- `docs/operations.md` 的升级/回滚一节：**新版能读老库、老版读不了新库**（schema 兼容口径）——
  那是**存储层**的兼容策略，与这里说的 **HTTP 契约**版本是两套东西，别看混。
